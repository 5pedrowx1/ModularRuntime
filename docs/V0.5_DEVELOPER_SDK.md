# ModularRuntime v0.5.0 — Developer SDK & Plugin Templates

External C# developers can create, build, validate, test, and package plugins with standard .NET
tooling, without knowing the engine, the loader, the daemon, or IPC:

```powershell
dotnet new modularruntime-plugin -n MyFirstPlugin
dotnet modularruntime validate --build
dotnet modularruntime pack
```

The result is a ZIP that the Plugin Manager installs (Store → Install from ZIP) as a local,
unverified package, or that is submitted with its source for official review.

## Fixes carried over from v0.4.x

### Versioning

The previous update was described as v0.4.1, but its `VersionPrefix` remained `0.4.0`. The product
version is now `0.5.0` in one property, and `AssemblyVersion`/`FileVersion` are derived from it.
The plugin API version is a separate property (`0.3`). See [VERSIONING.md](VERSIONING.md).

### Unload tracking

`PluginRuntime.WaitForUnloadAsync` removed a plugin's weak references from the tracking
dictionary **before** waiting. After a timeout or cancellation, contexts that were still alive
were no longer tracked, and a repeated wait reported "unloaded". References also accumulated
across restarts when nobody waited, and every wait forced garbage collections.

The new internal `RetiredLoadContextTracker`:

- removes an entry only after it is observed dead, so timeouts and cancellations keep live
  entries and waits can be repeated;
- prunes collected entries whenever a context is tracked or queried, so references do not accumulate;
- keeps weak references only, is thread-safe, and never holds its lock while waiting;
- forces nothing by default (`PluginUnloadWait.Observe`). `InduceCollection` is used only by the
  daemon's update and removal, and by diagnostics;
- exposes `GetPendingUnloadCount`.

The new end-to-end tests found a second retention source: **System.Text.Json** caches
reflection-emitted accessors per type in the shared context and evicts them only lazily. A plugin
that serialized its own types stayed in memory after it stopped. Reproduced: an embedded host
reported `UNLOADED False PENDING 2`. When collection is induced, the runtime now first flushes
those caches through the handler System.Text.Json declares with the public
`MetadataUpdateHandlerAttribute` (the Hot Reload cache contract).

Tests:

- `RetiredLoadContextTrackerTests` (8, deterministic)
- `UnloadTrackingTests` (5, real collectible contexts, including a plugin that deliberately
  keeps itself alive and a plugin that uses System.Text.Json)

## Plugin API 0.3

`IPluginContext.Descriptor` exposes the plugin's validated manifest (name, version, API version,
entry assembly and type, start order). This is the only contract change. Samples and fixtures now
declare `"apiVersion": "0.3"`.

### Reused, not duplicated

- **Manifest rules:** the Loader's reader. The new `PluginLoader.ValidateManifestAsync` runs the
  same rules without requiring the built assembly.
- **Package format and verification:** `PackageBuilder` writes the integrity manifest and the
  deterministic ZIP; `PackageVerifier` (the daemon's verifier) backs `inspect`.
- **Building:** only `dotnet build`. The tool never compiles, loads, or runs plugin code.
- **Assembly checks:** `System.Reflection.Metadata` (metadata tables, not loading).

## Security

- `pack` writes no `integrity.sig` and holds no key. Packages are *Local, unverified* in the daemon.
- `inspect` verifies like the daemon and never downgrades an unknown signature to "unsigned".
- `prepare-submission` excludes secrets and keys. Its hashes identify the delivery; they do not
  approve it. Official packages still go through review, a controlled rebuild, approval, and
  official signing ([PLUGIN_SUBMISSION_GUIDE.md](PLUGIN_SUBMISSION_GUIDE.md)).

## Limitations

- Packages are local (not on nuget.org) and declare no license or repository URL, because none
  is defined yet.
- `pack` produces deterministic ZIPs for the same build output. Bit-identical rebuilds also
  depend on the compiler's deterministic build (enabled by default) and the same SDK.
- `validate` evaluates the project with MSBuild and `--build`/`pack` run its build: build only
  projects you trust.
- Template option values (`--topic`, `--service-id`, `--extension-point`) are not validated by
  `dotnet new`. An invalid name fails at run time with `invalid_identifier`. An invalid
  `--plugin-id` is reported by `validate`.
- System.Text.Json caches are flushed only when collection is induced. With `Observe`, a plugin
  that used reflection-based serialization is collected after the serializer's own lazy eviction.
- No Visual Studio extension. The template package is a standard `dotnet new` package with
  classifications and a `dotnetcli.host.json`, the format Visual Studio uses to show installed
  .NET CLI templates. Display in Visual Studio was not verified (only the .NET CLI was tested).
