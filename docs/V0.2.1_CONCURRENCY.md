# v0.2.1 — Concurrency audit and fixes

v0.2.1 is a stabilization release. It adds no features, keeps the plugin API at
`0.2`, and keeps `ModularRuntime.Contracts` `AssemblyVersion` at `0.2.0.0`. The
product, Engine, Loader, and Host versions are now 0.2.1.

## Summary

The audit covered `OwnedResource.ReleaseAsync` and `OwnershipScope.BeginClose` /
`CloseAsync`. **Both had real, reproducible defects.**

Before fixing anything, 10 deterministic tests were written; 8 of them failed against the
v0.2.0 code. The most serious failure showed the engine releasing a plugin's factory, and
therefore requesting unload of its load context, while that plugin's resource cleanup was
still running. After the fixes, all 175 tests pass in Debug and Release (the 164 existing
tests are unchanged, plus 11 new ones).

## Defects found

### 1. `OwnedResource.ReleaseAsync` reported completion too early

In v0.2.0 the code was:

```csharp
if (Interlocked.Exchange(ref _released, 1) != 0) return;   // second caller returns at once
if (removeFromScope) Scope.Remove(this);                     // leaves the scope immediately
await ReleaseCoreAsync();
```

This caused three problems:

- **Concurrent `DisposeAsync`.** The second caller returned immediately while the first
  release (for example a slow `IAsyncDisposable` tracked with `Resources.Track`) was still
  running. The caller was told the resource was released when it was not.
- **Explicit dispose concurrent with scope close.** The explicit `DisposeAsync` removed the
  resource from its scope *before* releasing it, so a concurrent `CloseAsync` did not see it.
  `CloseAsync` finished, the engine detached the instance, released the factory, and
  requested unload while plugin cleanup code was still running.

  This is reachable without any misuse: a plugin that starts disposing a resource from
  `ShutdownAsync` without awaiting it, or a plugin thread disposing a handle while the host
  stops the plugin.
- **Scope close concurrent with explicit dispose.** When the release was started by
  `CloseAsync`, a later explicit `DisposeAsync` also returned immediately.

### 2. `CloseAsync` did not wait for cancellation callbacks started elsewhere

`BeginClose` sets `Closing` under the lock and then calls `CancellationTokenSource.Cancel()`
outside the lock. Cancellation callbacks run synchronously on that thread.

If `CloseAsync` ran on another thread while those callbacks were still running, its own
`BeginClose()` returned `null` (the scope was already closing) and it carried on. It then:

- released resources while the callbacks were still executing; and
- could dispose the token source underneath the running `Cancel()`. This happened when no
  invocation was in flight, or when the last in-flight invocation exited during the callbacks.

`Cancel()` and `Dispose()` must not overlap, so this race could surface as spurious errors
from `Cancel()`, which were then misreported as callback failures.

A second problem: concurrent `CloseAsync` calls were not coordinated. The second call returned
an empty result immediately.

**Reachability in the engine.** Today the engine calls `BeginClose` and `CloseAsync`
sequentially from the same teardown flow, under the plugin's gate, so the engine itself did
not hit this race. The scope API allowed it, though, and the fix makes `OwnershipScope` safe
on its own rather than relying on its caller's ordering.

## Fixes

### Shared release operation (`OwnedResource`)

- **Release state.** Release state is a single `TaskCompletionSource`, installed with
  `Interlocked.CompareExchange`. The first caller starts the release. Every concurrent or later
  caller awaits the same task and observes the same outcome, including the same exception
  instance.
- **Callers.** Callers are explicit `DisposeAsync`, `OwnershipScope.CloseAsync`, and removal of
  an extension point (which releases its contributions).
- **Becoming inactive.** The resource becomes inactive (`IsReleased`) as soon as the release
  starts, so no new invocation is admitted. This invalidation point is unchanged.
- **Leaving the scope.** The resource leaves its scope's list only after the release has
  finished, successfully or not. A concurrent `CloseAsync` therefore always finds it and waits
  for it.
- **No double dispose.** `ReleaseCoreAsync` runs exactly once. A failed release is not retried.
- **Exceptions are never swallowed.** Every exception from `ReleaseCoreAsync`, fatal ones
  included, is placed on the shared task, so awaiters never hang and never miss a failure.

### Coordinated close (`OwnershipScope`)

- **`BeginClose`** publishes a `cancellationCompleted` task under the lock when it moves to
  `Closing`, and completes it in a `finally` after `Cancel()` returns. Callbacks still run
  outside every internal lock.
- **`CloseAsync`** is one shared operation: concurrent and later callers get the same task and
  the same result. It runs these steps in order:
  1. Await `cancellationCompleted`, even when another thread started the cancellation.
  2. Enter `Closed` and take the remaining resources.
  3. Release each resource, or join a release already in progress. Releases run sequentially,
     newest first (the documented order is unchanged).
  4. Dispose the token source if no invocation is in flight.
- **Token source disposal.** The token source can only be disposed in the `Closed` state, which
  is reached after `Cancel()` has returned. Either `CloseAsync` disposes it, or the last
  invocation to exit does (unchanged). `Cancel()` and `Dispose()` therefore never overlap, and
  the token source is disposed exactly once.
- **Failure reporting.** A failure is reported by `CloseAsync` only for releases it started. A
  release started explicitly by the owner reports its failure to that caller. Each failure is
  reported exactly once and is not hidden.
- **No retained plugin objects.** Faulted tasks and exception variables are cleared in the async
  state machines, following the v0.2.0 rule that runtime state machines must not keep objects
  from plugins alive.

### Why this is not unnecessary complexity

The fixes replace a flag with a task in two places and add one `await`. No new locks, threads,
or public API were introduced. The lock discipline is unchanged: there are no nested locks and
no owner code runs under a lock.

## Remaining risks

- **Cleanup that never completes.** A resource cleanup (`IAsyncDisposable`) or a cancellation
  callback that never completes now blocks the teardown of its owner indefinitely, because the
  engine refuses to request unload while cleanup is pending. This is the deliberate trade-off:
  correctness first. There is no cleanup timeout. Like other lifecycle timeouts, it needs an
  explicit policy and is a v0.3 candidate.
- **Outgoing calls during resource release.** Resources released by `CloseAsync` run after the
  scope is `Closed`, so their disposal code cannot publish events or call services
  (`scope_closed`). Cleanup that needs the platform belongs in `ShutdownAsync`. This is
  unchanged from v0.2.0 and documented.
- **Resource listings during release.** `GetResources()` lists a resource whose release is
  running until the release completes. This is intentional: the resource is still owned.
- **Unobserved failures.** If a plugin starts a failing release and never observes the returned
  task, .NET reports the exception as unobserved when the task is collected. The engine does
  not report it again (it did not start that release).
- **Platform.** Only Windows has been validated.
