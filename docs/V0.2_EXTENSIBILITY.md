# v0.2.0 — Extensibility Platform

v0.2 turns ModularRuntime from a plugin loader with a lifecycle into an extensibility
platform. Plugins and hosts can now:

- communicate through an **event bus**;
- provide and consume **services**;
- declare and fill **extension points**.

Everything they create is tracked by **resource ownership** and cleaned up automatically.

The architecture of v0.1.1 is preserved: Contracts / Engine / Loader / Host, one shared
`PluginRuntime` for the standalone and embedded hosts, `IPluginInstanceFactory`, and one
collectible `AssemblyLoadContext` per plugin with `AssemblyDependencyResolver`. The engine
still knows nothing about assembly loading.

## Versions

| Item | v0.1.1 | v0.2.0 |
| --- | --- | --- |
| Product version | 0.1.1 | **0.2.0** |
| Plugin API version (`PluginApiVersion.Supported`, manifest `apiVersion`) | 1.0 | **0.2** (experimental) |
| `ModularRuntime.Contracts` `AssemblyVersion` | 1.0.0.0 | **0.2.0.0** |
| Engine / Loader / Host `AssemblyVersion` | 0.1.1.0 | 0.2.0.0 |

**Policy.** ModularRuntime is pre-release, so the plugin API is 0.x. Any 0.x minor version may
contain breaking changes.

- **Manifests:** a manifest must declare exactly `0.2`.
- **Loader:** the loader requires a plugin's reference to `ModularRuntime.Contracts` to have the
  same major.minor (`0.2`). Plugins built for v0.1 (API `1.0`) are rejected at discovery with
  `api_version_incompatible`.
- **From 1.0 onward:** the rule becomes "same major, minor ≤ supported", and the contracts
  assembly version stays fixed for the whole major line.

No compatibility layer for v0.1 plugins exists (decision: the project is unreleased).

## Public API overview

All contracts live in `ModularRuntime.Contracts`, in a single namespace, organized in folders.
One `using ModularRuntime.Contracts;` gives a plugin author the whole SDK.

```text
IPlugin                      InitializeAsync / ShutdownAsync (unchanged)
IRuntimeScope                Owner, Events, Services, Extensions, Resources
 └─ IPluginContext           + InstanceId, PluginId, Logger, StoppingToken
Events/      IPluginEventBus, PluginEvent, PluginEventCallback, IEventSubscription,
             EventPublishOptions, EventPublishResult, EventDeliveryResult, EventSubscriptionInfo
Services/    IPluginServiceRegistry, PluginServiceDefinition, PluginServiceDescriptor,
             IServiceRegistration, IPluginServiceClient, ServiceInvocationOptions
Extensions/  IExtensionRegistry, ExtensionPointDefinition/Descriptor,
             ExtensionContributionDefinition/Descriptor, IExtensionPointRegistration,
             IExtensionContribution, ExtensionInvocationResult
Invocation/  JsonPayload, PluginInvocationHandler, PluginRequest, PluginResponse,
             PluginInvocationResult (shared by services and contributions)
Ownership/   ResourceOwner, ResourceOwnerKind, ResourceKind, ResourceInfo,
             IPluginResource, IResourceScope
RuntimeName  identifier rules for topics, services, points, contributions, operations
```

**Host access.** The hosting application uses exactly the same interfaces through its own scope:

- `PluginRuntime.Host` (or `PluginEngine.Host`) returns the host's `IRuntimeScope`.
- `PluginRuntime.RuntimeId` identifies the runtime instance.
- `GetResources(pluginId)` lists what a plugin instance owns.

There are no singletons or static registries; every runtime instance is fully isolated.

### Why this shape

- **One scope type, two kinds of owner.** `IPluginContext` extends `IRuntimeScope`, so hosts and
  plugins use the same API. The scope decides who owns what was created, which is what
  automatic cleanup needs.
- **Small focused interfaces.** Events, services, extensions, and resources are separate
  interfaces rather than one large context.
- **One invocation model.** Services and contributions share a single invocation model
  (`PluginInvocationHandler` → `PluginResponse` → `PluginInvocationResult`) and a single
  internal engine (`HandlerInvoker`).
- **Neutral data only.** Only neutral data crosses plugin boundaries: `JsonPayload` (validated,
  immutable JSON text), strings, `Version`, `Guid`, and records defined in Contracts.

### Error model

| Situation | Behaviour |
| --- | --- |
| Programming errors (null arguments, malformed identifiers or definitions) | `ArgumentException` / `ArgumentNullException` |
| State and registration errors | `PluginRuntimeException` with a stable `ErrorCode`: `scope_closed`, `engine_disposed`, `duplicate_service`, `duplicate_extension_point`, `duplicate_contribution`, `extension_point_not_found`, `extension_point_unavailable`, `extension_version_incompatible`, `reentrant_lifecycle_operation` |
| Publications and invocations | Never throw for runtime conditions. They return structured results (`PluginOperationStatus` `Succeeded` / `Failed` / `Rejected` / `Canceled`, plus `ErrorCode`, `Message`, and a text-only `PluginDiagnostic`). |

`PluginErrorCodes` lists every code.

## Event Bus

```csharp
var subscription = context.Events.Subscribe("example.greetings", (e, ct) =>
{
    context.Logger.LogInformation($"{e.Source}: {e.Payload.GetString("text")}");
    return ValueTask.CompletedTask;
});

var result = await context.Events.PublishAsync(
    "example.greetings",
    JsonPayload.FromNode(new JsonObject { ["text"] = "hello" }),
    new EventPublishOptions { CorrelationId = "c-1" });
// result.Status, result.Deliveries (per subscriber: status, error code, diagnostic)
```

### Events

- **Topics** are exact-match `RuntimeName`s (lowercase, digits, `.` `_` `-`, ≤ 128 characters).
  There are no wildcards.
- **Each event carries:**
  - `EventId`;
  - topic;
  - payload;
  - `Source` (`ResourceOwner`: runtime, host or plugin, instance);
  - UTC timestamp;
  - optional correlation ID (≤ 128 characters);
  - immutable string metadata (≤ 32 entries).
- **Payload limit:** payloads are limited to `RuntimeLimits.MaxPayloadBytes` (default 256 KiB,
  UTF-8). Larger payloads are rejected with `payload_too_large`. Invalid JSON cannot become a
  `JsonPayload`.

### Dispatch

- **Sequential, in subscription order.** Each handler is awaited before the next one runs.
  `PublishAsync` completes when every delivery has completed.
- **Failure isolation.** A failing handler is reported (`Failed`, `handler_failed`, diagnostic,
  warning log) and delivery continues with the remaining subscribers.
- **Snapshot.** Dispatch uses the subscriptions that exist when the publication starts:
  - a subscription created during dispatch receives only later events;
  - a subscription removed during dispatch receives no further invocations;
  - invocations already running complete normally.
- **Subscriber shutdown.** Subscriptions whose owner is shutting down are skipped. Their
  in-flight handlers observe cancellation on the handler token.
- **Nested publishing.** Publishing from inside a handler is supported. Nesting is bounded by
  `RuntimeLimits.MaxEventDispatchDepth` (default 16, error `event_dispatch_depth_exceeded`), so
  infinite event loops fail explicitly.
- **Cancellation.**
  - The handler token is linked to the publisher's token and to the subscriber's scope.
  - A canceled publication reports undelivered subscriptions as `Canceled`.
  - Handlers that ignore their token cannot be interrupted.

### Ownership

- Every subscription belongs to the subscribing instance, not to the permanent plugin ID.
- `DisposeAsync` on the subscription removes it immediately and is idempotent.
- Subscriptions that are not disposed are removed when the instance stops or fails.

## Service Registry

```csharp
// Provider
context.Services.Register(
    new PluginServiceDefinition("example.text.transform", "Text transformation",
        new Version(1, 0), ["uppercase", "reverse"]),
    (request, ct) => ValueTask.FromResult(
        PluginResponse.Success(JsonPayload.FromNode(new JsonObject { ["text"] = "..." }))));

// Consumer
var client = context.Services.GetClient("example.text.transform", minimumVersion: new Version(1, 0));
var result = await client!.InvokeAsync("uppercase", payload, ct);
```

- **One provider per service ID.** Duplicate registrations throw `duplicate_service`.
- **Version policy.** The provider must have the same major version and a version ≥ the
  requested minimum. Otherwise the call is rejected with `service_version_incompatible`, or
  `GetClient` returns `null`.
- **Rejected before the handler runs:**

  | Condition | Error code |
  | --- | --- |
  | Unknown service | `service_not_found` |
  | Provider shutting down | `service_unavailable` |
  | Registration removed (through a client) | `service_removed` |
  | Undeclared operation | `operation_not_supported` |
  | Oversized request | `payload_too_large` |
  | Caller has stopped | `scope_closed` |

- **Handler outcomes:**

  | Outcome | Error code |
  | --- | --- |
  | Handler throws | `handler_failed`, with a diagnostic |
  | Handler-reported failure | the handler's own code, for example `invalid_payload` |
  | Handler returns `null` | `invalid_response` |
  | Oversized response | `payload_too_large` |
  | Canceled | `operation_canceled` |

- **Consumers never see provider objects.** `IPluginServiceClient` stores only the service ID
  and the registration ID, and resolves the registration on every call.
- **Inactive handles stay inactive.** When the bound registration is removed, the handle is
  permanently inactive (`service_removed`), even if another provider later registers the same
  ID. A consumer can keep an inactive handle without keeping the old provider alive (tested with
  real load contexts, scenario B).
- No dependency injection between plugins.

## Extension Points

```csharp
// Host (or a plugin) declares a point
host.Extensions.DeclareExtensionPoint(new ExtensionPointDefinition(
    "example.document.exporters", "Document exporters", new Version(1, 0)) { Operations = ["export"] });

// A plugin contributes
context.Extensions.Contribute(
    new ExtensionContributionDefinition("markdown", "example.document.exporters", new Version(1, 0))
    { DisplayName = "Markdown exporter" },
    ExportAsync);

// The host discovers and invokes
var contributions = host.Extensions.GetContributions("example.document.exporters");
var all = await host.Extensions.InvokeAllAsync("example.document.exporters", "export", payload);
```

- **Who declares points.** Points are declared by the host or by plugins.
- **Contributing.** A contribution targets an existing point. Contracts are compatible when
  they have the same major and the contribution's minor is ≤ the point's minor. Otherwise the
  runtime throws:
  - `extension_point_not_found`;
  - `extension_version_incompatible`;
  - `duplicate_contribution` (the ID is unique within a point).
- **Operations.** A point may restrict the operations its contributions accept (an empty list
  means unrestricted).
- **Invocation.** `InvokeAsync` calls one contribution. `InvokeAllAsync` calls every active
  contribution sequentially, in contribution order, and aggregates the results. A failing
  contribution does not stop the others.
- **Ownership.**
  - If the owner of a point stops or disposes the registration, the point and all its
    contributions are removed: contributors' handles become inactive and the contributions are
    removed from the contributors' scopes.
  - If a contributor stops, only its contributions are removed.
- **Immutable descriptors.** Descriptors are snapshots. Metadata is copied into read-only
  dictionaries, so later changes to the caller's dictionary have no effect.

## Resource Ownership

Every host and every plugin instance has an ownership scope. These resources belong to the
owner that created them:

- subscriptions;
- service registrations;
- extension points;
- contributions;
- objects tracked with `context.Resources.Track(name, IAsyncDisposable)`.

Each resource is identified by `ResourceOwner(RuntimeId, Kind, PluginId?, InstanceId?)`, a
`ResourceId`, and a `ResourceKind`. Host resources are owned separately from plugin resources.

Scope states are `Open`, `Closing`, and `Closed`:

| | Open | Closing | Closed |
| --- | --- | --- | --- |
| Create resources | yes | `scope_closed` | `scope_closed` |
| Incoming invocations to the owner's handlers | yes | rejected / skipped | rejected / skipped |
| Outgoing calls by the owner (publish, invoke) | yes | **yes** (so `ShutdownAsync` can use the platform) | `scope_closed` |

Resources are released sequentially, in reverse registration order. Release is a single
shared operation (since v0.2.1, see [V0.2.1_CONCURRENCY.md](V0.2.1_CONCURRENCY.md)):

- explicit disposal and automatic cleanup never release a resource twice;
- every caller, concurrent or later, awaits the same release and observes its outcome;
- a resource stays owned (and listed) until its release completes, so the owner's teardown
  waits for releases started by anyone, including fire-and-forget disposals, before the
  factory is released and unload is requested;
- release failures are collected and reported once (to whoever started the release), and do
  not stop the remaining releases.

### Teardown order (stop, failed start, disposal)

1. **Close the scope.** No new resources and no new incoming invocations. In-flight handler
   tokens are canceled; cancellation callbacks run outside every lock.
2. **Cancel `StoppingToken`.** This stops the plugin's own background work.
3. **Drain in-flight handlers.** The drain is bounded by `RuntimeLimits.DrainTimeout`
   (default 10 s; `Timeout.InfiniteTimeSpan` waits indefinitely). On timeout a `drain_timeout`
   warning is logged and teardown continues.
4. **`ShutdownAsync`.** After a failed start this is a best-effort rollback shutdown.
5. **Release every remaining owned resource.** Registries drop the handler delegates.
6. **Detach the instance and dispose its lifetime token source.** Then hop to a fresh
   thread-pool stack (see the memory model).
7. **Release the factory.** This requests unload of the load context.

Engine disposal stops plugins in reverse start order and then closes the **host** scope last,
so host subscribers and host extension points stay usable while plugins shut down.

### Status of a stop

| Failure | State | Error code |
| --- | --- | --- |
| `ShutdownAsync` failure | `Failed` | `shutdown_failed` |
| Release failure of a tracked resource | `Failed` | `resource_cleanup_failed` (the other resources are still released) |
| Factory release failure | `Failed` | `release_failed` |

In every case all cleanup steps still run.

### Reentrancy

A stop requested from code that runs on behalf of the same plugin would wait for itself. That
code can be:

- one of the plugin's handlers;
- its `InitializeAsync` / `ShutdownAsync`;
- a callback chain started from them, such as plugin handler → event → host handler → `StopAsync`.

The engine tracks the owners whose code is executing in the current asynchronous flow, using
GUID-only frames. Such a stop returns `Rejected` with `reentrant_lifecycle_operation` instead of
deadlocking. `DisposeAsync` called from inside any callback of the runtime throws a
`PluginRuntimeException` with the same code.

Stopping *another* plugin from a handler is allowed. Because frames flow with the execution
context, work started from a handler counts as part of that flow. Request such stops outside the
callback, for example from the host's main loop.

## Concurrency model

- **Locks.** There is one private lock per component: event bus, service registry, extension
  registry, each ownership scope, each plugin slot, and the engine registry. There is no global
  lock.
- **No nested locks.** No lock is held while another lock is acquired, so no lock inversion is
  possible. Owner state is always read outside registry locks.
- **No owner code under locks.** Handlers, cancellation callbacks, disposables, and loggers run
  without any runtime lock held.
- **Copy-on-write subscriptions.** Subscriptions are copy-on-write arrays per topic. A
  publication takes the lock only to read the snapshot.
- **Two checks before a handler runs.** Every invocation is admitted through the owner's scope:
  an in-flight counter, rejected once the scope is closing. The registration's release flag is
  then checked again. Together these define when a removal becomes effective, and let the
  engine drain exactly the invocations that started.
- **Lifecycle serialization is unchanged.** One gate per plugin, as in v0.1.1.

## Memory model and unload

The runtime never keeps a strong reference to a plugin object after its instance stops:

- **Registries.** Registries hold handler delegates only while a registration is active. Release
  clears the delegate.
- **Public types are text-only.** Descriptors, results, events, `ResourceInfo`, log entries, and
  `PluginErrorInfo` contain only text, numbers, GUIDs, `Version`, and Contracts records.
  Exceptions become `PluginDiagnostic` immediately.
- **Handles and frames.** Client handles and invocation frames contain only identifiers.
- **Stack hygiene.** Two kinds of hidden roots were found by the real load-context tests and
  fixed:
  1. **Hoisted locals.**
     - Debug builds hoist every local of an `async` method into its state machine, including
       `catch` variables and the `ValueTask` returned by a plugin handler. (A plugin async
       method's task is an instance of a generic type over a plugin type, which pins the plugin's
       load context.)
     - A state machine is cleared only *after* its caller's synchronous continuations have run.
     - The runtime therefore clears such locals before continuing, and does not use `await`
       inside a `catch` that receives plugin exceptions.
  2. **Continuations on top of plugin frames.**
     - When plugin code completes asynchronously, the code awaiting it resumes on top of the
       plugin's frame. So does anything that completes synchronously after it, such as the
       caller of `StopAsync`.
     - The runtime awaits a `ThreadPoolHop` after teardown and after asynchronously completed
       handlers, so callers always continue on a stack without plugin frames.

Unload is still cooperative. A load context is collected only when nothing references it, and
the runtime cannot prevent references the plugin creates itself, for example:

- static events on shared types;
- threads that keep running;
- `GCHandle`s;
- handlers that ignore cancellation and are still running.

Tests force a GC only to observe collection; the runtime never forces a GC.

## Standalone host and embedded framework

Both hosts compose the same `PluginRuntime`. Neither has its own bus or registry.

**Standalone CLI commands** (new commands in bold):

- `plugins list | info | start | stop | start-all | stop-all`;
- **`plugins resources <id>`**;
- **`events subscriptions [topic]`**;
- **`events publish <topic> [json]`**;
- **`services list`**;
- **`services info <id>`**;
- **`services invoke <id> <operation> [json]`**;
- **`extensions list`**;
- **`extensions contributions <point-id>`**.

Ctrl+C and stdin-EOF graceful shutdown are unchanged.

**EmbeddedExample** demonstrates the full embedding flow:

1. The host declares `example.document.exporters`, registers its own `host.clock` service, and
   subscribes to `example.greetings`.
2. It discovers and starts the plugins in start order.
3. It publishes an event and invokes `example.text.transform`.
4. It discovers and invokes the exporter contributions.
5. It inspects owned resources, then stops and disposes the runtime.

**Start order.** Manifests may declare `"startOrder"` (an integer from -10000 to 10000, default
0). `StartAllAsync` starts plugins in ascending order, with ties in registration order.
`StopAllAsync` and disposal use the reverse order. The demos rely on this for a predictable
sequence (subscribers and providers at 10, publishers and consumers at 20, contributor at 30,
failure demo at 40), not on alphabetical discovery order.

## Creating a plugin (v0.2)

1. Create a class library targeting `net10.0` with `EnableDynamicLoading=true`, referencing only
   `ModularRuntime.Contracts`.
2. Implement `IPlugin`. In `InitializeAsync`:
   - subscribe, register services, declare points, or contribute through the context;
   - track your own disposables with `context.Resources.Track`.

   Nothing needs to be undone in `ShutdownAsync`: the runtime releases it all.
3. Exchange data only as `JsonPayload`. To serialize your own DTOs, use your own
   `JsonSerializerOptions` instance; shared static caches keyed by your types can delay unload.
4. Honor the cancellation tokens passed to handlers and `context.StoppingToken`.
5. Add a `plugin.json` with `"apiVersion": "0.2"` and, optionally, `"startOrder"`.

See [PLUGIN_DEVELOPMENT.md](PLUGIN_DEVELOPMENT.md) for the manifest reference.

The 78 v0.1.1 tests were kept. Seven lines in four test files were adapted to intentional
contract changes; no test was removed:

- `TestDescriptors` uses `PluginApiVersion.Supported` instead of `1.0`.
- The loader test expects API `0.2`.
- `PluginLoadException.Code` became `PluginRuntimeException.ErrorCode`.
- `PluginSlot.AttachInstance` takes the ownership scope.

The test fixture manifests and the sample manifests were updated to `apiVersion` `0.2`.

**Validation of the tests themselves.**

- **Mutation checks.** Each critical mechanism was disabled in turn. 7 of 8 mutants were
  detected:
  - cancellation outside the scope lock (test fails);
  - reentrancy detection (the test run hangs in a real deadlock);
  - drain before `ShutdownAsync` (detected only after the drain tests were given real
    asynchronous cleanup after cancellation; the first version of those tests let the
    mutant through);
  - the thread-pool hop after handlers;
  - clearing of the start exception;
  - subscription removal;
  - service handler removal.

  Not observable: clearing the pending handler task in `finally`. On every path where the
  host checks unload, the teardown hop has already moved the caller to a fresh stack. The
  clearing is kept as defense in depth.
- **Negative control.** A reflection-based test copies a plugin's handler delegate out of the
  bus, and requires that the load context then *stays alive*.

## Limitations

- **Trust model.** Plugins are trusted and run in-process. `AssemblyLoadContext`, the event bus,
  the service registry, and extension points provide **no** security isolation. Any plugin can
  call any service and subscribe to any topic.
- **No forced interruption.** Handlers or lifecycle methods that ignore cancellation cannot be
  interrupted. The drain timeout bounds the wait, but such code keeps running and keeps its load
  context alive until it returns.
- **Sequential event dispatch.** A slow subscriber delays the publisher and later subscribers.
  There is no per-subscriber queue or parallel dispatch.
- **No general timeouts.** Lifecycle operations (`InitializeAsync`, `ShutdownAsync`) and
  invocations have no timeouts; only draining has one.
- **Exact matching only.** Topics have no wildcards. Payloads are JSON text with no schema
  validation.
- **Reentrancy detection is conservative.** It is based on the asynchronous flow, so background
  work started from a handler counts as that owner's flow.
- **Thread-pool hops.** The hop adds one thread-pool hop per asynchronously completed handler
  invocation and per teardown.
- **Platform.** Only Windows has been validated.
