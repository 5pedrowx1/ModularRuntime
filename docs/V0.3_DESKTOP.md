# v0.3.0 — Independent Runtime & WPF Desktop

v0.3 moves the runtime out of any user interface. One background process per
user profile owns the engine and every plugin; a command-line client and a WPF
desktop client control it over a local, current-user-only named pipe. Closing a
client never stops the runtime.

Related documents:

## Processes

| Executable | Subsystem | References | Owns |
| --- | --- | --- | --- |
| `ModularRuntime.Daemon.exe` | Windows (no window) | Loader, Contracts, Ipc | `PluginRuntime`, plugins, event bus, services, extensions, log store, IPC server |
| `ModularRuntime.Cli.exe` | Console | Ipc only | One connection per command |
| `ModularRuntime.Desktop.exe` | Windows (WPF) | Ipc only | One supervised connection and the UI |

The clients do not reference the engine, the loader, or the plugin contracts, so
they cannot host plugins even by accident. The former interactive console host
(`ModularRuntime.Host`) was removed; its project became the daemon and its
command processor became the CLI commands.

### Profiles and data

All state lives under a profile directory: `--profile`, else
`MODULARRUNTIME_PROFILE`, else `%LOCALAPPDATA%\ModularRuntime`.

```text
config/daemon.json     pluginDirectory, logBufferCapacity, shutdownTimeoutSeconds,
                       autoStartPlugins, maxMessageBytes (unknown keys rejected)
logs/daemon-*.log      daily log files
plugins/<id>/          plugin installations (default plugin root)
runtime/daemon.json    pid, ids, version, start time, pipe name of the running daemon
desktop/settings.json  desktop preferences (theme, start daemon on launch, log auto-scroll)
```

Each profile has its own pipe and lock (both derived from the user SID and the
profile path), so separate profiles run separate daemons side by side; the tests
rely on this.

## Daemon

- Single instance per user and profile; concurrent starts produce exactly one
  daemon (others exit with code 2).
- Plugins are discovered at startup; `--auto-start` starts them all.
- Stops only on an explicit request (`runtime.shutdown`) or a termination signal
  (session end, console close). Shutdown stops every plugin in reverse order,
  bounded by `--shutdown-timeout` (default 30 s, exit code 3 when exceeded).
- Exit codes: 0 graceful, 1 startup failed, 2 already running, 3 shutdown timeout,
  4 invalid arguments or configuration.
- Logs: ring buffer (default 5000 entries) with sequence numbers, daily files, and
  live subscriptions with per-client drop accounting.

## CLI

```text
modularruntime [--profile <dir>] [--json] [--timeout <sec>] <command>

status
daemon start [--auto-start] | daemon stop
plugins list | info <id> | start <id> | stop <id> | start-all | stop-all
services list | extensions list | events subscriptions
logs [--follow] [--level <level>] [--plugin <id>] [--category <name>] [--search <text>] [--limit <n>]
```

| Exit code | Meaning |
| --- | --- |
| 0 | Success |
| 1 | The operation ran and failed (plugin failure, daemon exited with a non-zero code) |
| 2 | Usage error |
| 3 | Daemon unavailable (not running, unreachable, could not be started) |
| 4 | The daemon rejected the request (validation, unknown plugin, daemon stopping, incompatible protocol version) |
| 130 | Canceled (Ctrl+C) |

`daemon start` returns once the daemon accepts connections; `daemon stop` returns
once the daemon process has exited and reports its exit code. `start-all` and
`stop-all` treat plugins already in the target state as success. `logs --follow`
subscribes, prints history, fills the gap by sequence, and reports dropped entries.

## Desktop application

WPF on `net10.0-windows`, MVVM without third-party libraries.

**Shell.** Custom window chrome (`WindowChrome`) with a dark Fluent-like theme
(light theme in Settings), per-monitor DPI awareness (v2 manifest), a sidebar
with Dashboard, Plugins, Events, Services, Extensions, Logs, Settings, and a
connection indicator with Connected, Connecting, Starting, Stopping,
Disconnected, or Error plus a status message.

**Themes.** Two complete palettes (`Themes/Colors.Dark.xaml`, `Themes/Colors.Light.xaml`)
with the same keys; every view and control style references them through
`DynamicResource`, and no XAML outside the palettes contains color literals
(both enforced by tests). `ThemeService` swaps the merged palette, located by its
`ThemeName` key, so a change applies immediately to every open window, popup,
menu, tooltip, and dialog. The saved theme is applied before the main window is
created, so startup shows no frame of the other palette. Confirmations use a themed
WPF dialog instead of the system MessageBox. Dark is the default.

**Window frame.** The main window and dialogs ask DWM for Windows 11 rounded
corners (`DWMWA_WINDOW_CORNER_PREFERENCE = DWMWCP_ROUND`), a border color from the
palette (`DWMWA_BORDER_COLOR`), and the matching frame mode
(`DWMWA_USE_IMMERSIVE_DARK_MODE`). `WindowChrome` uses
`GlassFrameThickness="0,0,0,1"`: with `0`, WPF clips the window with a
rectangular window region, which defeats native composition; with a non-zero
frame there is no region, no `AllowsTransparency`, and DWM draws corners, border,
and shadow. Maximized and snapped windows are square, as DWM decides. On Windows 10
the attributes are unavailable and the window keeps square corners.

**Pages.**

- *Dashboard* — daemon state, version, pid, uptime, plugin counts, services,
  extension points, subscriptions, connected clients, folders.
- *Plugins* — searchable list with state filters; per-plugin Start/Stop with a
  busy indicator; Start all / Stop all (Stop all asks for confirmation when
  plugins are running); details with entry point, owned resources, and the last
  error with a copyable diagnostic.
- *Events* — subscriptions and per-topic statistics.
- *Services* — registered services with provider and version.
- *Extensions* — extension points and their contributions.
- *Logs* — live stream with level, plugin, and text filters, pause/resume with a
  pending counter, auto-scroll, local clear, copy, and markers for disconnection,
  missed entries, dropped entries, and daemon restart.
- *Settings* — theme, start daemon on launch, log auto-scroll, daemon
  information, data folders, Start daemon, and **Stop daemon** (confirmation that
  states how many plugins will be stopped).

Every page has explicit Loading, Empty, Ready, Error, and Disconnected states.
All data comes from the daemon; nothing in the UI is mocked.

**Connection.** `RuntimeConnection` runs one background supervisor:

- connects to the profile's pipe; if no daemon answers and *start daemon on
  launch* is enabled, starts one (first attempt only);
- subscribes to `state.changed`; pages reload snapshots on change;
- on loss: shows Disconnected, clears stale data, reconnects with backoff
  1 s → 10 s; *Retry* reconnects now; *Start daemon* starts the daemon explicitly;
- never restarts a daemon that stopped or crashed on its own, and after an
  explicit Stop waits for the user.

**Threading.** IPC events arrive on background threads and are marshaled with
`Dispatcher.BeginInvoke`; there are no `.Result`, `.Wait()`, or blocking calls on
the UI thread. Async commands disable themselves while running (no duplicate
clicks) and route failures to a visible message. The log page queues streamed
entries and drains them on a 150 ms UI timer in batches, capped at 5000 entries.

**Closing.** The window's `Closing` handler cancels the close, disposes the
connection (unsubscribe, disconnect), and then closes. It sends no shutdown
request. The daemon and its plugins keep running.

Command-line options: `--profile <dir>`, `--no-autostart`.

## Publishing

```powershell
./scripts/publish.ps1 [-Configuration Release] [-Runtime win-x64] [-Output <dir>] [-SelfContained]
```

Publishes the three projects into one folder (default
`artifacts/publish/win-x64`), framework-dependent unless `-SelfContained`, and
checks that the three executables are present. Development builds use the same
side-by-side layout in `artifacts/app/<Configuration>/`. The clients locate the
daemon next to themselves, or through `MODULARRUNTIME_DAEMON_PATH`.

## Engine changes

The plugin API is unchanged (`0.2`, contracts `AssemblyVersion` `0.2.0.0`).
Internally the engine gained a **state version**: `PluginEngine.StateVersion`
and `WaitForStateChangeAsync(knownVersion, cancellationToken)` (also on
`PluginRuntime`). Plugin slots and ownership scopes report changes through a
callback invoked outside their locks; the engine does not call into IPC code.

### Manual validation

Done on Windows 11 with the Debug build against a separate profile: the desktop
app started the daemon, showed live updates caused by CLI commands, survived the
daemon being stopped (Disconnected with Retry/Start daemon) and restarted it;
closing the window left the daemon and its running plugin untouched; reopening it
connected to the same daemon process. Pages were reviewed visually (dashboard,
plugins, logs, services, settings, disconnected state).

## Bugs found during validation

**Daemon kept the launcher's output open.** `Process.Start` always passes `bInheritHandles = TRUE` to `CreateProcess`. A
daemon started by `ModularRuntime.Cli daemon start` therefore inherited the
CLI's redirected stdout pipe and kept it open for its whole life, so any script
capturing that command's output hung until the daemon exited. The launcher now
creates the daemon with `CreateProcess` directly, without handle inheritance, in
a new process group, and outside the caller's job when the job allows breakaway.

**Elevated clients could not reach a normal daemon.** `PipeOptions.CurrentUserOnly`
compares the pipe owner with the client token's default owner, which is
`BUILTIN\Administrators` in an elevated process. An administrator terminal
running the CLI was refused by the user's own non-elevated daemon ("pipe was not
owned by the current user"). The daemon now always sets the user SID as owner,
and the client verifies the owner itself (user SID, or token default owner for
older daemons) before sending any data. Verified against a running non-elevated
daemon from an elevated shell.

## Limitations

- Windows only. The trust boundary is the user account: any process of the same
  user can administer that user's daemon. Remote and cross-account access are
  denied by the pipe ACL, but were not exercised by tests (single-account test
  machine).
- The daemon is not a Windows Service and does not start at logon (the desktop
  setting for that is intentionally absent).
- Plugins are discovered only at daemon startup; installing a plugin requires a
  daemon restart. A stopped or failed plugin cannot be started again without a
  restart (engine rule since v0.1; lifted later, see [STORE_AND_RESTART.md](STORE_AND_RESTART.md)).
- Clients cannot publish events or invoke services.
- A launcher inside a kill-on-close job object that forbids breakaway can still
  take the daemon down with it.
- Shutdown at session end is best effort within the time Windows grants.
- The custom maximize button does not show Windows 11 snap layouts.
- WPF UI behavior is covered by view model tests and manual checks, not by
  automated UI tests.
