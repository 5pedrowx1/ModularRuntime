# Versioning policy

ModularRuntime has two independent version numbers.

| Version | Current | Where it is defined | Changes when |
|---|---|---|---|
| **Product version** | `0.6.0` | `VersionPrefix` in `Directory.Build.props` | every release |
| **Plugin API version** | `0.3` | `ModularRuntimePluginApiVersion` in `Directory.Build.props` and `PluginApiVersion.Supported` in `ModularRuntime.Contracts` | only when the plugin contracts change |

## Product version

One value for every executable, library, and NuGet package of a release: the daemon, the
desktop app, the CLI, the developer tool (`dotnet modularruntime --version`), and the packages
`ModularRuntime.Contracts`, `.Sdk`, `.Engine`, `.Loader`, `.Templates`, `.DevTools`.

- `AssemblyVersion` and `FileVersion` are derived from `VersionPrefix` (`0.6.0.0`), so they cannot drift.
- `ModularRuntime.Contracts` is the exception for `AssemblyVersion` (see below); its
  `FileVersion` and package version still follow the product.
- The daemon reports the product version (`status`, the desktop app's connection panel) and
  uses it for the registry's `minimumRuntimeVersion` checks.
- The templates reference the `ModularRuntime.Sdk` package of the same product version. The
  version is substituted when the template package is built.

## Plugin API version

The plugin API is experimental while ModularRuntime is pre-release (0.x).

- A plugin declares `apiVersion` in `plugin.json`. For a 0.x API the runtime requires exactly the
  supported `major.minor`, because any 0.x minor may contain breaking changes. From 1.0 onward
  the rule becomes "same major, minor less than or equal to the supported one".
- The `ModularRuntime.Contracts` assembly identity follows the API: `AssemblyVersion` is
  `major.minor.0.0` (`0.3.0.0`). The loader shares one Contracts assembly with every plugin;
  a plugin compiled against other contracts is rejected (`api_version_incompatible`) before it
  is loaded. `dotnet modularruntime validate` reports the same mismatch from metadata.
- Raising the product version never changes the API version by itself.

### History

| API | Product | Change |
|---|---|---|
| 0.1 | 0.1.x | Lifecycle only |
| 0.2 | 0.2.0 – 0.4.x | Event bus, service registry, extension points, ownership |
| 0.3 | 0.5.0 – 0.6.0 | `IPluginContext.Descriptor` (the plugin's validated manifest: name, version, …) |

Plugins built for API 0.2 must be rebuilt against the 0.5.0 packages and declare
`"apiVersion": "0.3"`. No other source change is needed.

v0.6.0 changed no plugin contract: the API stays `0.3` and plugins built for 0.5.0 run unchanged.

## Other formats with their own versions

| Format | Version | Notes |
|---|---|---|
| Registry catalog (`registry.json`) | schema `2` since 0.6.0 | adds status, provenance, revoked keys; 0.6 reads schemas 1 and 2; 0.4/0.5 read only 1 and reject 2 |
| Submission (`submission.json`) | schema `2` since 0.6.0 | adds license, source repository and commit, lock files; the validator rejects schema 1 with guidance |
| Approval record (`approval.json`) | schema `2` since 0.6.0 | signed, bound to a build record; the unsigned v0.4 record is accepted for test keys only |
| Integrity manifest, signature envelope, trust store | `1` | unchanged |

The demo catalog (generated by the administrator's tools with TEST keys) reads the product and
API versions from `Directory.Build.props`, so its entries always target the current API and runtime.

## Packages and compatibility

A plugin references `ModularRuntime.Sdk` (or only `ModularRuntime.Contracts`) of the product
version it targets. The SDK assembly is private to each plugin; Contracts is shared with the host
and is never packaged with a plugin (`dotnet modularruntime pack` excludes it).
