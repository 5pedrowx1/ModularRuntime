# v0.1.1 — Stability & Reliability Update

v0.1.1 is a maintenance release. It hardens concurrency, memory retention, and
failure handling in the existing architecture. It adds no new features.

| Item | Value |
| --- | --- |
| Product version | `0.1.1` (`AssemblyVersion` `0.1.1.0` for Engine, Loader, Host) |
| Plugin API version | `1.0` (unchanged) |
| `ModularRuntime.Contracts` `AssemblyVersion` | `1.0.0.0` (unchanged) |
| Architecture | Unchanged: Contracts / Engine / Loader / Host, shared `PluginRuntime`, `IPluginInstanceFactory`, one collectible `AssemblyLoadContext` per plugin, `AssemblyDependencyResolver` |

## Summary of changes

### 1. Concurrency: cancellation outside the state lock

`CancellationTokenSource.Cancel()` runs registered callbacks synchronously, and
those callbacks are plugin code. In v0.1.1, `PluginSlot` never calls `Cancel()`
while holding its `_sync` lock:

- `CancelLifetime()` reads the lifetime source under the lock, increments an
  in-flight cancel counter, releases the lock, and only then calls `Cancel()`.
- `DetachInstance()` clears the instance and lifetime under the lock. If no
  cancel is in flight it disposes the source; otherwise it marks the source for
  release and the last `CancelLifetime()` to finish disposes it.
- Result: the source is disposed exactly once, never while a callback is still
  running, and `DetachInstance()` never waits for a callback.
- Callback exceptions (aggregated by `Cancel()`) are reported as a
  `cancellation_callback_failed` warning with a text diagnostic and never
  prevent shutdown, rollback, or factory release.
- Callbacks may read engine state from other threads, or call `StopAsync` for
  the same plugin, without deadlocking.

### 2. Graceful shutdown during initialization

Before v0.1.1, `DisposeAsync` waited on a plugin's gate while that plugin was
still inside `InitializeAsync`, so a slow initialization delayed shutdown with
no cancellation signal.

Now disposal first cancels the lifetime of every instance that is still
initializing (`PluginSlot.CancelLifetimeIfInitializing`). The lifetime is linked
into the initialization token, so a cooperative plugin stops initializing. A
start that attaches its instance just after that pass observes the shutdown flag
and cancels its own lifetime. The ordering is enforced by the slot lock: either
disposal sees the attached lifetime, or the start sees the flag.

The start result is `Canceled` with `operation_canceled` ("…because the engine
is shutting down"). The instance is rolled back (`ShutdownAsync` best-effort)
and marked `Failed`, and its factory is released. Running plugins are **not**
cancelled early; they are still stopped in reverse registration order.

### 3. Memory retention and AssemblyLoadContext unload

Exception objects thrown by plugins keep the plugin's collectible load context
alive. They do this through the exception type, and through stack-trace
keep-alive data for frames in collectible assemblies. The negative control
described below confirmed this with an `OperationCanceledException` thrown by
`Task.Delay` inside a plugin.

- `PluginDiagnostic` (Contracts) is an immutable, text-only snapshot of
  `ExceptionType`, `Message`, `StackTrace`, and `Detail` (`ToString()`).
- `PluginOperationResult`, `LogEntry`, and `PluginDiscoveryError` expose
  `Diagnostic` and contain no `Exception` properties. A test enforces this by
  reflection.
- `PluginLoadException` derives from `PluginRuntimeException` and carries a
  `Diagnostic` instead of an `InnerException`. Plugin constructor failures
  (`TargetInvocationException`) are converted to text at the loader boundary.
- `PluginErrorInfo` (retained as `LastError`) stores the diagnostic.
- The scoped plugin logger converts exceptions passed to
  `IPluginLogger.Log(..., exception)` to text before calling the host logger.
- The engine converts plugin exceptions to a diagnostic at once and clears its
  reference before awaiting rollback or factory release. Messages are built from
  `diagnostic.Message`, not from `exception.Message`.

### 4. Defensive diagnostic capture

`PluginDiagnostic.FromException` never throws. Each member (`Message`,
`StackTrace`, `ToString()`) is read on its own, and a placeholder replaces any
member whose getter throws. Before this change, a plugin exception with a
throwing `Message` escaped from the engine's `catch` handlers. That left the
plugin in a transitional state.

### 5. Best-effort logging

A host `IRuntimeLogger` that throws used to propagate out of engine operations
between state transitions. This could leave a plugin in `Stopping` or `Loaded`
with its instance still attached. The engine (`Internal/SafeLogger`) and the
loader (`Internal/SafeLogger`) now catch non-fatal logger exceptions. Plugin
logging through `IPluginLogger` never throws into plugin code because of a host
logger failure.

### 6. Other fixes

- Disposal wraps each per-plugin stop in a defensive handler. An unexpected
  failure for one plugin cannot stop the others from being stopped and
  released.
- A `release_failed` stop result now includes the release diagnostic.
- The standalone host strips a UTF-8 BOM from input lines. Windows PowerShell
  5.1 adds one when it pipes to stdin, so the first command used to fail as
  "Unknown command".
- Fixed a copy-paste error in the `LoggingFailurePlugin` fixture log message.
- `LIFECYCLE.md` described the stop order wrongly. `ShutdownAsync` runs before
  the instance is detached.

## Compatibility notes

- **Plugins:** `IPlugin`, `IPluginContext`, `IPluginLogger`, and
  `PluginLoggerExtensions` are unchanged. Plugins built against API `1.0` load
  and run unchanged; the HelloPlugin and FailingPlugin samples were not
  modified.
- **Hosts:** removing the exception properties from host-facing result and log
  types, and the inner exception from `PluginLoadException`, is a
  source-breaking change for hosts that read them. Use `Diagnostic` instead.
  The Contracts `AssemblyVersion` stays `1.0.0.0` as required. A host compiled
  against the v0.1.0 types must be recompiled.

## Tests

78 tests in total, all passing in Debug and Release (v0.1.0 reported 43). The
repository has no commit history, so the table lists only the v0.1.1 test
classes that can be identified for certain:

| Suite | Tests | v0.1.1 test classes |
| --- | --- | --- |
| `ModularRuntime.Engine.Tests` | 49 | `PluginSlotCancellationTests` (8), `PluginEngineCancellationTests` (2), `PluginEngineReliabilityTests` (13) |
| `ModularRuntime.Loader.Tests` | 16 | — |
| `ModularRuntime.Integration.Tests` | 13 | `PluginExceptionUnloadTests` (5), `PluginReliabilityUnloadTests` (4) |

Scenarios covered:

- **Cancellation and reentrancy:**
  - synchronous callbacks run once;
  - callbacks can read state on the same thread and from another thread;
  - `DetachInstance` does not wait for a blocked callback and defers disposal;
  - concurrent cancels invoke the callback once;
  - callback failures are reported;
  - cancel after detach does nothing;
  - a reentrant `StopAsync` from a callback does not deadlock.
- **Concurrency:** a stress test runs 20 iterations × 8 plugins with concurrent
  `StartAsync`, `StopAsync`, and `DisposeAsync`. Each plugin must end in
  `Validated`, `Stopped`, or `Failed`, its factory must be released exactly
  once, and it must be shut down exactly as many times as it was initialized.
- **Exceptions:**
  - hostile exceptions during initialization, shutdown, factory creation, and
    cancellation callbacks;
  - rollback shutdown failure;
  - a throwing host logger during start, stop, start failure, and plugin
    logging.
- **Graceful shutdown:**
  - disposal cancels an in-progress initialization;
  - disposal does not cancel running plugins before their ordered stop.
- **Unload (`WeakReference`):** each test keeps every result, `PluginRuntimeInfo`
  snapshot, and log entry, then requires the plugin load context to be
  collected. Covered failures: initialization, shutdown, constructor
  (`PluginLoadException`), plugin logging, hostile exception, cancellation
  callback, and disposal during initialization. All of them use exception types
  defined in the plugin assembly.

### Test validation

- **Mutation check:** the logger-isolation, diagnostic-hardening, and
  dispose-cancellation fixes were each disabled in turn. Eight reliability tests
  failed, which shows the tests detect these defects.
- **Negative control for unload tests:** a static list in the engine kept the
  plugin exception alive. Three unload tests failed, which shows the
  `WeakReference` checks detect real retention.
- **Flakiness:** the engine and integration suites passed 5 times in a row in
  both Debug and Release.

### Manual validation

- **Standalone host:**
  - `plugins list`, `start-all`, `info`, `stop`, and `exit` all work;
  - FailingPlugin is isolated and reported with a text diagnostic;
  - HelloPlugin starts and stops;
  - closing stdin without `exit` triggers a graceful shutdown, exit code 0;
  - a missing plugin directory is reported.
- **EmbeddedExample:** discovers both plugins, starts and stops HelloPlugin,
  and disposes the runtime, exit code 0.

## Known limitations

- **No timeouts.** A plugin that ignores its cancellation token in
  `InitializeAsync`, `ShutdownAsync`, or a cancellation callback can still block
  that operation and therefore disposal. Start/stop timeouts are v0.2 work.
- **Factory creation is not cancelled by disposal.** `IPluginInstanceFactory.CreateAsync`
  receives only the caller's token. Disposal waits for creation to finish, and
  the start then cancels itself once the instance is attached.
- **Collection is cooperative.** A plugin that keeps references to itself from
  outside its load context still prevents unload. Examples: static events on
  shared types, threads that keep running, or `GCHandle`s.
- **Logger failures are silent.** There is no fallback channel for a host logger
  that keeps failing.
- **Ctrl+C was not re-tested.** The host's Ctrl+C handler is unchanged from
  v0.1.0 and was not re-tested interactively in this update. Graceful shutdown
  was tested through stdin EOF and the `exit` command.
- **Platform.** Only Windows has been validated.
